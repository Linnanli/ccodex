# 线程归档入口、预热清理与撤销边界

先前待查的 `TTC-V-04` 归档调用位于预热管理器构造参数中，用于丢弃云端预热线程，属于支撑机制。实际用户归档入口另在会话菜单中找到。两者使用相同的协议方法，但调用条件和生命周期不同，不能据方法名合成同一用户功能。

这项纠正已进入 [v4 功能清单](feature-scope-v4.json)及 [CSV](feature-scope-v4.csv)。原 71 个根候选全部保留，其中旧归档候选改归支撑；另增一个有具体控件来源的用户归档根候选。现在为 72 个根候选、拆分 WSL 容器后 74 个行为条目：50 个用户操作、21 个支撑和 3 个入口待审。46 项功能定义对应 [200 条尚未执行的功能规格](feature-scope-v4-scenarios.json)，完整产品分母仍未知。

## 已厘清的调用与职责

1. 会话菜单 `hn` 经导入绑定使用 `jJo` 的普通归档项与 `Jda` 的归档操作。关联 automation 或活动状态可先要求确认；特殊受限删除分支另行保留。
2. `Jda` 通过 `KI` 选取的 RPC 调用归档，可由 `Hda` 登记撤销/重做。UI 回调本身不返回后台 Promise。侧栏 `oqo/nqo` 可在后台确认之前先隐藏行。
3. 所选 `Dfn` 实现中，`archiveConversation → lrn/srn → drn` 管理归档顺序并发送 `thread/archive`。**实际 UI 所选 RPC 是否接到该实例仍未知**；这里保留接口实现合同，不将其写成运行时已连通。
4. `urn` 管理取消订阅、移除待归档记录、后台取消归档、hydration 与按条件恢复置顶；`r4t` 单独负责缓存驱逐。
5. `Pdn.discardPrewarmedThread` 对云端预热调用 archive，对非云端预热调用 delete；重复丢弃只触发一次。它不属于用户归档控件。

[17 条源码事实、29 个范围与 5 组导入/导出绑定](thread-archive-entry-contracts.json)保存逐项依据。恢复时据此分开维护菜单/确认、撤销调度、归档状态流程、缓存清理、预热资源清理五种职责；发布 chunk 继续只作来源定位。

## 会改变实现的失败语义

| 条件 | 所选源码的效果 | 恢复要求 |
| --- | --- | --- |
| 普通归档 | 先抑制显示、登记 archiving 与 pending，再请求后台 | 行消失不能作为后台成功依据 |
| pending 写入失败 | 不发送后台归档请求 | 分开报告准备失败与后台失败 |
| 后台归档请求失败 | 清理 archiving；新加的抑制可撤回，pending 可能仍在 | 不补造全面回滚 |
| 后台已接受、随后缓存驱逐抛错 | 操作仍可能报错，后台归档已经发生 | 不因错误提示自动重试或取消归档 |
| 指定的 no-rollout 错误 | 进入 inactive 归档/缺失项处理的条件分支 | 不将所有错误合并为该回退 |
| 撤销归档 | 先准备 owner 并移除 pending，再请求后台；接受后 hydration 也可能失败 | 分别记录后台结果、本地恢复和置顶恢复 |

置顶读写、后台广播及特定 metadata 清理有各自的容错边界。活动线程处理取决于 aeon/受限运行时条件，不能把普通归档实现成通用的取消任务。
