## 工具与分析方式

REA 使用 [morluto/rea](https://github.com/morluto/rea)。REA 负责提供入口、模块关系、IPC 和源码位置等分析证据；编码代理负责归纳功能、建立归属清单，并通过源码检查和行为观察验证结论。

执行前固定 REA 的实际版本，记录 Node.js 版本、执行命令、输入范围及输出中的限制。先用小型 JS 样例验证工具能成功启动分析 worker，再处理应用归档。CLI 与 MCP 结果均保存原始返回值。对于环境启动失败、截断、解析失败、动态调用和未解析关系，记录原因并安排补充调查，不能计入已完成分析。

以下示例采用已核对帮助信息的 REA npm 发布版 `6.4.0`；实际执行时替换冻结输入路径，并保存 stdout、stderr、退出码和执行时间：

```bash
REA_VERSION='6.4.0'
TARGET_ASAR='/绝对路径/冻结副本/app.asar'
npx -y "rea-agents@$REA_VERSION" analyze-javascript-application "$TARGET_ASAR" --format json
```

该发布版支持 `--max-heap-mb`、`--analysis-timeout-ms`、`--artifact-format` 和 `--integrity-policy`；参数以固定版本的实际 `--help` 为准。GitHub 主分支文档可能包含尚未发布的能力。大文件的语义分析可能因节点预算或资源限制只得到部分结果，需检查输出中的限制并安排定向补充分析，不能以命令成功退出作为完整分析的判据。

ASAR 分析之外还需检查 `app.asar.unpacked`、相关资源和辅助程序。JS 分析不要求先配置原生反编译器；遇到与 Codex 功能有关且无法通过公开源码解释的原生边界时，再选择适用工具。

## 分析步骤

### 第一阶段 固定输入与文件清单

1. 记录版本、构建号、平台、CPU 架构、应用入口以及实际 Electron 或定制运行时信息。
2. 保存只读分析副本，覆盖 ASAR、unpacked 文件和必要的辅助资源；对输入生成哈希和文件清单。
3. 识别 JS、HTML、CSS、资源、原生模块、Wasm、可执行文件及包元数据；记录归档内外的关联关系。
4. 查找外置及内联 source map，检查是否包含 `sourcesContent`，记录源码覆盖范围。
5. 核对构建脚本引用的文件和上级工程，列出存在、缺失及来源未明的构建输入。

交付：基线清单、文件清单、source map 覆盖情况和初始构建缺口。发布归档作为分析证据保留，不进入最终客户端恢复源码目录。

### 第二阶段 功能范围盘点

以代码中的路由、菜单、命令、快捷键、设置项、功能开关及处理函数建立功能候选清单，再对照实际界面和可触发行为核实。

调查范围包括会话与项目管理、消息与流式展示、任务执行与取消、审批、文件与变更查看、终端、设置、窗口和系统集成。上述条目是调查方向；每项实际功能及其边界以基线证据为准，并继续收录分析发现的其他 Codex 功能。

每项功能记录：

| 字段 | 内容 |
| --- | --- |
| 标识与名称 | 稳定的功能标识、用户可理解的名称 |
| 触发入口 | 页面、菜单、快捷键、命令或后台事件 |
| 行为 | 输入、输出、状态变化、失败与取消行为 |
| 使用条件 | 平台、账户、功能开关、服务或环境条件 |
| 模式归属 | `codex`、`chatgpt`、`shared`、`unknown` |
| 代码链路 | 入口、关键模块、IPC、后台服务、数据存储 |
| 证据与状态 | 来源标识；静态确认、行为确认或待验证 |
| 恢复验证 | 后续能够判断该功能已复刻的具体观察点 |

ChatGPT 专属功能的判定需要检查调用方、模式条件和共享依赖。名称或目录中的 `chat`、`chatgpt` 字符串只作为线索。无法确定归属的模块暂记为 `unknown`。

交付：功能范围清单和模式边界图；每个排除项都有理由，每个保留项都有可追踪的入口或使用路径。

### 第三阶段 第三方依赖识别

在架构深挖前先识别第三方边界，避免把公开库当作待恢复的业务源码。结合已安装包的元数据、导入、许可证声明、source map 和打包包装器判断来源。混合第一方与第三方代码的 chunk 按代码范围记录。

根 `package.json` 中的版本范围不等于实际安装版本。优先查找具体包版本与锁定证据；通过代码指纹推断的版本需单独标注置信度，不能当作已确认事实。

| 依赖情况 | 分析结果应提出的处理方式 |
| --- | --- |
| 已确认且未修改的公开包 | 声明准确依赖，后续生成锁文件 |
| bundle 内嵌的公开库 | 确定引用边界和接口，提出恢复为包导入的方案 |
| 同时存在多个版本 | 记录各版本及调用方，评估是否必须并存 |
| 修改过的上游库 | 记录修改证据，评估独立适配、补丁依赖或受维护版本，不默认用普通上游包替换 |
| 私有包或未知代码 | 保留调查项，明确取得源码或替代实现的可行性 |
| 原生模块与 Wasm | 记录版本、平台、架构、接口、源码来源和构建方式 |

每个条目包含名称、版本及其依据、来源、许可证线索、使用位置、运行时或构建时用途、模式归属、修改状态、建议引入方式和未解决问题。Codex 自己编写的依赖封装属于待恢复的第一方代码。

交付：第三方依赖清单、第一方与第三方归属表、版本和来源未解决清单。最终工程不生成第三方实现副本；临时分析副本与最终维护源码分开管理。

### 第四阶段 REA 架构与调用链分析

从确认的应用入口和功能入口出发，追踪第一方代码及保留功能的传递依赖。保留所有发现模块的归属记录，深度分析集中在 Codex 和共享模块。

1. 建立 main、preload、renderer、worker 和辅助进程的入口与生命周期关系。
2. 对 IPC 记录发送方、接收方、通道、请求与响应结构、通知、异常、超时和取消方式。
3. 对页面及状态记录路由、组件调用、状态所有权、订阅、持久化和恢复行为。
4. 对后台边界记录 app-server、命令行工具、MCP、原生接口和服务端接口的实际使用关系。
5. 对动态导入、计算得到的通道名、循环依赖、模块副作用和共享闭包补充验证。
6. 对无法直接解析的大 bundle，使用 AST 和作用域关系辅助分析，并保留原位置到格式化代码的映射。

模块边界先区分发布文件、可恢复的源码模块和为维护而提出的逻辑模块。chunk 不自动等同于业务模块；没有足够证据时保留较粗边界。

对 Codex app-server，检查客户端实际使用的能力与选定公开版本之间的差异。公开 app-server 是候选集成方案，采用与否由覆盖情况决定；不能仅凭接入成功就认为桌面功能已全部恢复。

交付：进程和模块图、IPC 契约、状态与数据流、后台能力差异，以及带来源的模块归属清单。

### 第五阶段 行为与依赖验证

对主要功能链执行可重复的行为观察，将运行结果与静态推断对照。具有文件修改或命令执行效果的流程使用独立测试目录和样例数据。

覆盖正常完成、失败、取消、重启恢复等有实际实现依据的路径。记录测试条件、动作顺序、预期与实际结果，以及支持或修正了哪些结论。事件记录使用与任务相关的最小样例，避免把个人会话或凭据写入分析产物。

账户、平台或服务条件不满足时，保留对应功能及其静态证据，标明待验证条件。源码可达但界面未出现、界面存在但处理路径不完整等差异，都进入问题清单。

交付：行为验证记录、可用于后续回归验证的场景，以及静态与运行结果的差异清单。

### 第六阶段 形成实施依据

汇总前五阶段结果后，再提出：

- 由模块职责、运行环境和共享关系决定的源码目录与包边界。
- 从原始文件或代码范围到拟恢复模块的映射。
- ChatGPT 专属功能剥离清单及共享依赖保留理由。
- 第三方依赖引入方案，以及原生、Wasm、定制运行时和私有组件的处理决定。
- 缺失构建输入的补齐方案和公开 app-server 的适用范围。
- 根据依赖关系排列的功能恢复顺序、阶段验收和完整功能覆盖表。
- 基于固定版本证据、协议与行为差异的后续升级方式。

交付：分析报告和逆向实施计划草案。构建工具与客户端目录在此阶段确定，避免用预设目录解释未知代码。

## 证据与交付格式

每条结论必须能回到固定版本中的原始证据。源码位置优先记录文件哈希、字节范围或 AST 位置；格式化后的行号需要附带文件哈希及映射，不能单独充当定位依据。

证据记录至少包含：`id`、`baselineId`、`claim`、`sourcePath`、`sourceHash`、`locator`、`method`、`confidence` 和 `verificationStatus`。

`confidence` 使用 `confirmed`、`inferred`、`unresolved`；`method` 区分静态代码、包元数据、运行观察和推断。静态确认只证明代码或契约存在，不自动代表运行路径已经验证。

功能、模块、依赖与问题清单通过证据标识关联。模块清单至少包含职责、运行环境、模式归属、来源范围、导入导出、共享状态、副作用、第三方依赖和拟议路径。未知信息显式保留，不填入猜测值。

建议分析产物按以下目录组织。这是分析资料目录，不代表未来客户端源码目录：

```text
analysis/<baseline-id>/
  baseline.json             # 版本、输入哈希、工具版本和执行条件
  files.json                # 文件类型、入口、归档位置和来源分类
  raw/                      # REA 原始结果及补充工具输出
  evidence.jsonl            # 可追溯证据记录
  features.csv              # 功能范围与模式归属
  modules.json              # 模块归属和依赖关系
  ipc.json                  # IPC 与跨进程接口
  dependencies.csv          # 第三方和外部运行时依赖
  behavior-checks.md        # 行为观察与验证场景
  gaps.md                   # 未知项、构建缺口和下一步调查动作
  report.md                 # 分析结论与覆盖统计
  implementation-plan.md    # 分析完成后生成的实施计划草案
```

原始安装包和大体积提取结果使用单独的本地存放位置，由基线清单引用；后续创建分析目录时配置相应忽略规则。文档、结构化清单和必要的小型证据可纳入版本管理。

## 分析完成标准

- [ ] 输入版本和哈希已固定，分析结果未混用版本。
- [ ] 已登记所有发现的文件、入口和功能候选，并说明分析覆盖的范围。
- [ ] 已区分 Codex、ChatGPT 专属、共享和未知项，排除理由可追溯。
- [ ] 每个保留功能已追踪到足以说明其职责的模块和关键跨进程或外部边界。
- [ ] 第三方依赖有版本与来源依据；无法确认的条目列出调查动作。
- [ ] 原生、Wasm、辅助程序、定制运行时和私有服务均有独立记录。
- [ ] Source map 覆盖、构建输入缺失、REA 解析限制和动态关系均有说明。
- [ ] 主要行为与静态结论已对照，未验证项有明确触发条件。
- [ ] 项目结构建议、恢复顺序和验收条件能够引用分析证据。

报告应分别统计已发现、已分类、已分析、已验证、已排除和未解决的数量，并给出分母。文件扫描完成不等于功能分析完成，抽样行为检查不等于全部功能已验证。

若存在会改变架构或影响完整复刻的未解决项，应交付阶段报告并继续定向分析。可以先安排证据充分的实施工作，但不能将这些缺口计为已完成，也不能默默缩小功能范围。

## 实施阶段需要守住的验收目标

完整功能清单需逐项验证；mock、占位页面和未解决依赖不计为完整复刻。客户端需使用独立应用标识和数据目录，在干净环境下安装、构建和打包，运行时无需读取原客户端安装目录。

项目应明确区分可从源码构建的组件和预编译依赖。仅复制原生二进制不能证明该组件已恢复源码；依赖远端能力的功能还需要可用的服务契约。上述条件在分析阶段调查，并在实施计划中落实为验收项。
